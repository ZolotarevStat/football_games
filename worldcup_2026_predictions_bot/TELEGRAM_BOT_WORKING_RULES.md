# Актуальные правила работы над Telegram-ботом

## 1. Базовый контракт

- Цель: поддерживать рабочий MVP турнира прогнозов, а не строить универсальную платформу.
- Runtime: Yandex Cloud Compute VM, `systemd` polling-worker, webhook отключён.
- Источник правды: Google Sheets.
- В памяти бота допустим только короткий черновик ввода между шагами.
- Локальный ноутбук не должен быть runtime для турнира.
- Перед каждым деплоем обязательны локальные и удалённые `unittest`.

## 2. Scope и stop-rules

P0:

- бот доступен участникам;
- прогнозы сохраняются и редактируются до дедлайна;
- дедлайны проверяются сервером;
- личные прогнозы не раскрываются в группе до публикации;
- `/my`, `/predict`, `/scores`, `/authors`, `/analytics` работают в личке;
- организатор может публиковать прогнозы, считать очки и отправлять leaderboard;
- worker переживает рестарт ВМ.

P1:

- удобные админские кнопки;
- понятные ошибки;
- снижение нагрузки на Google Sheets;
- улучшение визуала сообщений и таблиц;
- smoke/test инструкции.

Не расширять без явной причины:

- web UI;
- отдельная БД;
- webhook вместо polling;
- сложная авторизация;
- автоматический импорт результатов из внешних источников;
- админский ввод результатов через бота, пока Google Sheets быстрее и надёжнее.

## 3. Приватность и GitHub

- Не публиковать `.env`, service-account JSON, токены, VM IP, SSH-пользователей, локальные deploy scripts.
- Не публиковать реальные списки Telegram username участников.
- В публичных docs и fixtures использовать placeholders.
- Перед commit/push делать sensitive scan по diff.
- Локальные operational notes про секреты и VM можно держать только вне публичного репозитория.

## 4. UX Telegram

- Чувствительные пользовательские команды работают только в личке.
- В группе обычный текст игнорируется; пользовательские forecast-команды должны редиректить в личку.
- Публичные команды без привязки допустимы: `/help`, `/rules`, `/matches`.
- Для bounded choices использовать inline buttons.
- После клика удалять или заменять сообщения с inline keyboard, чтобы не оставались stale-кнопки.
- Для длинных списков показывать топ-5 и кнопку `Показать полный список`.
- После завершения действия показывать dashboard с кнопками дальнейших действий.
- Для power users оставить текстовые команды:
  - `/submit MATCH_ID scores | Автор1 | Автор2`;
  - `/scores MATCH_ID scores`;
  - `/authors MATCH_ID | Автор1 | Автор2`.

## 5. Валидация прогнозов

- Ровно 7 счетов.
- Все 7 счетов уникальны.
- Формат счёта: `N-N` или `N:N`.
- Счета идут в порядке вероятности.
- По одному автору Г+П из заявки каждой команды.
- Авторы в одном прогнозе не должны повторяться.
- В плей-офф прогнозный счет и Г+П считаются только за основное время матча; экстра-тайм и серия пенальти не учитываются.
- Уже использованных игроком авторов скрывать и блокировать в других актуальных прогнозах.
- После дедлайна новые прогнозы и правки блокируются сервером.
- При ручном вводе автора сначала проверять exact match по заявке; для близких вариантов давать suggestion.

## 6. Матчи и дедлайны

- `match_id` должен быть человекочитаемым и стабильным.
- Критичные поля матчей импортируются из canonical data, а дедлайн вычисляется кодом, если правило фиксированное.
- При импорте матчей/игроков обновлять только нужный лист, не перетирать unrelated data.
- После импорта проверять 2-3 живых примера в Google Sheets и перезапускать worker при необходимости.

## 7. Google Sheets

- Sheets остаётся source of truth для MVP.
- Append-only history хранится в `predictions_raw`.
- Текущее состояние хранится в `predictions_latest`.
- Писать в Sheets только на финальном подтверждении действия.
- Не читать широкие листы без необходимости.
- Использовать repository abstraction, чтобы bot flow тестировался через fake repository.
- Для quota:
  - кэшировать read-heavy листы внутри TTL;
  - сбрасывать кэш после успешных write;
  - не пересоздавать фильтры после каждого append/update;
  - использовать retry для 429/5xx;
  - если quota всё равно переполнена, вернуть пользователю forwardable-сообщение с желаемым изменением.
- Не спамить `/score all` и post-match flow несколько раз в минуту.

## 8. Ошибки и fallback

- Общий fallback допустим только для неизвестных ошибок.
- Если пользователь уже прошёл валидацию прогноза, но запись в Sheets упала по quota, бот должен написать:
  - что пользователь хотел сделать;
  - `match_id` и пару команд;
  - 7 счетов;
  - обоих авторов;
  - причину: переполнение квоты Google Sheets;
  - просьбу переслать сообщение организатору.
- Это нужно, чтобы пользователь не вспоминал ввод заново, а организатор видел предметную ошибку.

## 9. Админские правила

- `/admin` должен показывать актуальный справочник команд и кнопки.
- `/status` и `/status_latest` нужны для контроля сдачи прогнозов.
- `/publish MATCH_ID` публикует прогнозы после дедлайна и помечает их locked.
- `/insights MATCH_ID` показывает агрегаты прогнозов.
- `/score MATCH_ID` должен:
  - показывать очки по выбранному матчу;
  - обновлять cumulative `scoring`, `leaderboard` и analytics по всем матчам с результатами;
  - не обнулять leaderboard до одного матча.
- `/score all` пересчитывает все заполненные результаты.
- `/leaderboard` публикует текущий leaderboard в турнирный чат.
- Кнопка `Итоги матча` запускает серию:
  1. publish;
  2. insights;
  3. score;
  4. leaderboard.
- Результаты матчей для MVP заносятся вручную в Google Sheets, лист `results`.

## 10. Scoring и аналитика

- Автоголы не дают очки выбранному игроку.
- Отменённые матчи и технические результаты не учитываются.
- Источник голов и ассистов: sports.ru.
- В плей-офф в `results` заносится только основное время: счет, голы, ассисты и автоголы. Пенальти в основное время считается голом; экстра-тайм и серия пенальти после матча не учитываются.
- С 1/8 финала очки постепенно растут.
- Tie-breakers при равенстве очков:
  1. финал;
  2. матч за 3 место;
  3. 1/2;
  4. 1/4;
  5. 1/8;
  6. 1/16;
  7. группа.
- Поддерживать аналитические листы:
  - `leaderboard`;
  - `leaderboard_by_total`;
  - `leaderboard_by_score`;
  - `leaderboard_by_goals`;
  - `leaderboard_by_assists`;
  - `match_author_picks`;
  - `match_first_score_belief`;
  - `leaderboard_by_game_day`;
  - `leaderboard_by_tour`.

## 11. Деплой

Стандартный цикл:

1. Внести правку локально.
2. Прогнать `PYTHONPATH=src .venv/bin/python -m unittest discover -s tests`.
3. Скопировать только изменённые файлы на VM через `scp`.
4. На VM применить файлы в `/opt/wc-predictions-bot`.
5. Прогнать remote tests.
6. Перезапустить `wc-predictions-bot`.
7. Проверить `systemctl is-active wc-predictions-bot`.
8. Посмотреть свежие логи `journalctl`.
9. Проверить один live command в Telegram, если изменение пользовательское.

## 12. GitHub workflow

- Рабочая публичная папка: `worldcup_2026_predictions_bot`.
- В GitHub копировать только tracked/sanitized source, tests и docs.
- Перед commit:
  - тесты в публичном worktree;
  - `git diff --stat`;
  - sensitive scan по diff и новым файлам.
- Коммит должен описывать поведенческое изменение, а не внутреннюю механику.
- После push сверить чистый worktree.

## 13. Следующий план оптимизации Sheets

P1:

- row-index cache для `participants` и `predictions_latest`;
- `batchUpdate` для `mark_match_locked`;
- убрать повторные чтения одних и тех же листов внутри одной команды;
- разделить read ranges по реальной потребности команды.

P2:

- lightweight local cache на VM;
- SQLite hot path + periodic Sheets export только если Google Sheets останется bottleneck после P1.
